# The looseleaf profile of OKF v0.3

This document is the normative statement of the looseleaf profile. It is
banked from the Phase 1 design record, sections 4 and 6, confirmed at the
design gate on 2026-11-20. The `looseleaf check` command implements the
mechanical rules stated here. Where this document and the design record
differ, the design record governs until this document is amended on the
record in DECISIONS.md.

A looseleaf bundle is a directory of Markdown files with YAML
frontmatter that conforms to the Open Knowledge Format (OKF) at version
0.3 and to the additional rules below. Every rule is either an OKF rule
restated for memory or a looseleaf convention. Conventions travel through
the extension mechanisms the standard provides, so a generic OKF
consumer stays conformant on a looseleaf bundle and simply sees less.

## 1. Layout

The bundle root holds three files with fixed roles.

- `index.md` is the reserved bundle index. Its frontmatter carries
  `okf_version` set to `"0.3"`, a `title`, a one-sentence `description`
  and a `license`.
- `log.md` is the reserved bundle change history, newest date first.
- `claims.md` is a concept of type Claim Registry. It is generated by the
  tool from the daily and curated layers and is never edited by hand.

Content lives in layer directories, each mapped to one concept type.

| Directory     | Concept type   |
| ------------- | -------------- |
| `curated/`    | Curated Memory |
| `people/`     | Person         |
| `groups/`     | Group          |
| `topics/`     | Topic          |
| `daily/`      | Daily Log      |
| `bank/`       | Memory Bank    |
| `synthesis/`  | Synthesis      |
| `directives/` | Directive      |

Every directory carries an `index.md`. The `daily/` and `curated/`
directories also carry a `log.md`. Files named `index.md` and `log.md`
are reserved files under the standard and are never concepts. Daily Log
files are named by ISO date, `YYYY-MM-DD.md`, and the name must be a
real calendar date. The daily layer is append-only. Neither the tool
nor a synthesis pass ever edits a daily file.

A Person body keeps six sections, `## Facts`, `## History`,
`## The relationship`, `## In common`, `## Open threads` and
`## Strengthening`, the shape the source system uses, so a reader
finds the same anatomy on every person file. A person body missing
part of the shape is flagged as a warning.

## 2. Frontmatter

Frontmatter is written in the YAML subset defined in section 5. OKF
requires only `type`. Looseleaf requires the following on every concept
it manages, meaning every Markdown file in a layer directory other than
the reserved `index.md` and `log.md`, plus `claims.md`.

- `type`, one of the concept types in section 1, matching the directory
  the file sits in. The checker re-derives the expected type from the
  directory, which is the defence against a host writer dropping or
  rewriting the key.
- `title` and `description`. The description is the sentence index
  generators and other consumers show, written for a reader who has not
  opened the file.
- `generated`, a mapping with `by` and `at`. The synthesis pass stamps
  `process:looseleaf-synthesis`. A human author stamps `human` with
  their id. This key is what makes verification currency computable.

Further keys carry fixed meanings.

- `sources` is required on Curated Memory, Person, Group, Topic and
  Memory Bank concepts. Each entry names a `resource` that is either a
  path resolving inside the bundle or an absolute URL. Message-level
  provenance never goes in `sources`, because a message id does not
  resolve for a consumer. Message provenance lives in claim blocks.
- `verified` is written only when a verification actually happened, as
  a mapping with `by` and `at`, the actor who did it and when. A
  machine actor never stamps a human actor.
- `stale_after` is written only under the staleness rules in the
  synthesis contract. Inventing a review date is a contract breach.
- `status` and `superseded_by` are used exactly as the standard defines
  them. A replaced concept is deprecated and points at its replacement.
  Concepts are deprecated, never deleted, without a human gate.
- Extension keys carry the `x-looseleaf-` prefix, for example
  `x-looseleaf-rank`, the closeness rank on Person and Group concepts
  that drives index ordering. Unknown keys are preserved untouched by
  every looseleaf writer.

## 3. Claim blocks

A claim block is the unit of memory. It lives in a Daily Log body first
and in a Curated Memory body after promotion. Its shape is a list item
whose text opens with a kind and confidence tag, followed by indented
sub-items.

```markdown
- [fact|high] The user's name is David.
  - claim: f49ece3f572d99160cd755bd6798e855
  - quote: "Hey David, I'm your personal agent."
  - sources: message:fee78aee-ff6c-406c-b234-beec38239659
  - supersedes: 05ac4c1c26a93331e76cfba1d883f1da
```

- The tag is `[kind|confidence]`. Kinds in use are fact, event,
  preference, decision, state change, update and commitment.
  Confidences are high, medium and low.
- The `claim` sub-item carries the claim identity. Identities are
  stable, are never reused and never change when claim text is
  corrected.
- The `quote` sub-item carries a verbatim quote of the source.
- The `sources` sub-item carries message ids, in-bundle paths with a
  claim anchor, or URLs. In-bundle references name the file and the
  claim id inside it, never a line number, because line numbers rot on
  every edit.
- The `supersedes` sub-item is optional and names the claim this claim
  replaces, written on the new claim at birth. The reverse link is
  written only by the synthesis pass, into the curated layer and the
  claim registry, never into a daily file.
- The `superseded-by` sub-item is that reverse link. It names the
  claim that replaced this one. It appears only on the curated copy
  of a superseded claim, written by the synthesis pass when it
  promotes the replacement, and the claim it names must in turn name
  this claim in its own `supersedes` sub-item.

The chain rule is the whole convention. A claim is never edited in place
once a later daily log exists. Correction is a new claim that
supersedes. Promotion from the daily layer to the curated layer is a
copy that carries the identity, the quote and the sources unchanged. A
promoted claim whose wording differs from its daily original is drift,
because a wording change is a new claim, not a promotion. The curated
concept that holds a superseded claim carries a superseded claims
section listing the old text, the old identity, the replacing identity,
the date and a one-line reason. The section sits under a
`## Superseded claims` heading, and each entry is one list item of the
form `- ` then the old identity, the old claim text, the words
`Replaced by`, the replacing identity, the word `on`, the date, a
comma and the one-line reason.

## 4. The claim registry

`claims.md` joins every claim chain in the bundle into one index a
consumer can scan without opening every daily file. The registry is a
looseleaf convention layered on OKF v0.3. It is not part of the
standard, and it is never described as part of the standard.

The registry names every claim identity found in the daily and curated
layers. A superseded claim appears as withheld, on the same line as its
reason and the identity of its replacement, never silently dropped. A
registry whose identity set differs from the layers it indexes is
stale, and staleness is a check failure.

Regeneration is deterministic. The same bundle state rendered with the
same generated stamp produces byte-identical output. The date and the
reason on a withheld line come from the curated layer's superseded
claims section when the supersession has been promoted there, because
that section is where the synthesis contract puts them. Before
promotion, the date falls back to the daily file that carries the
replacing claim, and the line carries no reason rather than an
invented one.

## 5. The frontmatter subset

Looseleaf frontmatter is a deliberate subset of YAML, small enough to
parse exactly and to write byte-stably.

- Top-level `key: value` entries, one per line. Keys are bare words,
  digits, `-` and `_`.
- Scalar values are plain, double-quoted or single-quoted strings.
  Plain scalars run to the end of the line.
- A flow mapping `{ by: "process:x", at: "2026-11-20T00:00:00Z" }` and a
  flow sequence `[a, b]` on one line.
- A block sequence under a key, items introduced by `- ` at a deeper
  indent. An item is a scalar, or a mapping whose first entry follows
  the `- ` and whose remaining entries align under it.
- A block mapping under a key, entries at a deeper indent, one level
  deep. Values inside a block mapping and inside a block sequence
  item's mapping stay inline, as scalars or as flow forms on the
  entry line, so block collections never nest inside one another.
- Anything else, anchors, block scalars, tabs, deeper nesting, is
  outside the subset. A looseleaf reader rejects a file whose
  frontmatter falls outside the subset and reports it, rather than
  guessing.

## 6. The bank shape rule

A Memory Bank concept is a distilled view, not a dump. A bank concept
whose body runs past 250 lines is flagged as a shape finding for the
next synthesis pass. The rule exists because the conversion test found
a live bank file at roughly 250 times the size of its siblings, an
append dump that had lost its distilled shape. The flag is a warning.
The repair belongs to the synthesis pass under its contract, never to a
silent rewrite.

## 7. The synthesis contract

The synthesis pass is specified in full in
`skills/looseleaf-synthesis/SKILL.md`, which is the contract a host
agent executes. The mechanical half of that contract, layout,
frontmatter, provenance shape, chain integrity and registry currency,
is what `looseleaf check` verifies.
